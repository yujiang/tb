# 架构与流程

[返回目录](./index.md)

## 职责边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `Fight` | 阵营、单位查询、目标选择、输入/执行校验、完整 action、随机数、胜负 | 等待图形动画、账号鉴权 |
| `FightSide` | 本阵营单位、贡献统计及独立的ultimate实例 | 不驱动回合或结算整场行动队列 |
| `FightUltimate` | 每队一个，由FightSide持有；本队回合标记、单个待放大招及施放校验执行 | 不保存跨阵营数组；Fight在动作边界协调双方顺序，动画由FightLoop负责 |
| `FightMimic` | 全局最近攻击及每单位最近行动的输入副本与技能等级记录，普通/高级模仿 | 不缓存目标集合；选人、失效回退、普通指令和技能结算复用Fight，同一动作沿用原ctx与反应预算 |
| `FightLoop` | 初始化、全局回合、行动记录、插入位置、行动条、结束清理 | 每个技能的伤害公式 |
| `FightUnit` | 资源、状态、已学技能、装配槽、被动和 Buff | 替宿主加载业务角色数据 |
| `FightSkill` 与各 `func` | 攻击/治疗/毒/复活、倍率、子技能与效果 | 推进整场行动队列 |
| `FightBuff` 及派生类 | 持续效果、属性、状态、周期、事件监听与移除 | 选择怪物本次普通行动 |
| `FightBehavior` | AI与Rule共用的xls配置、单位绑定、监听清理、属性与生命周期钩子 | 选择行动或实现具体触发规则 |
| `FightAI` | 根据场面在 `waitInput` 决定普通行动；每怪一个 | 承载所有固定触发机制 |
| `FightRule` | 血轴、回合轴、受伤轴等固定触发机制；多条共存 | 抢占 AI 的普通输入决策 |
| `FightClient/Report/Mud` | 按增量消息维护/描述战斗表现 | 在客户端重新计算伤害 |

源码入口：[Fight](../../src/fight/Fight.ts)、[FightLoop](../../src/fight/FightLoop.ts)、[FightUnit](../../src/fight/Unit/FightUnit.ts)。

## 为什么不把 AI、Rule、Buff 都放进 Status

它们可以共用事件、属性修正和技能结算，但身份与生命周期有区别：AI 决定“这次做什么”，Rule 在条件满足时触发固定行为，Buff 是单位身上可添加/移除、有持续时间的效果。全部塞进 Status 后，输入、阶段计数、属性、驱散、行动插入会互相牵制，难以维护。

`FightRule` 与 `FightAI` 同级继承 `FightBehavior`：公共层保存xls、提供getXls并管理单位绑定、监听清理和生命周期钩子；FightRule表达固定触发规则，FightAI是抽象基类，统一技能选择与输入预检，具体findTarget负责选人；当前唯一内置实现FightAITarget把条件、自身/贡献/职业站位选人与技能组合为配置。AI不再是FightRule，规则列表入口仍明确拒绝AI实例。现有具体规则、AI和工厂入口保持原职责。

## 为什么技能主要用 func，Buff 则派生类

技能主要在一次 process 中执行，常见差异可以用目标、数值、子技能、效果与 `func` 组合表达。Buff 会跨输入、受伤、死亡、复活和回合边界，特殊 Buff 派生类是明确的扩展位置。

例如三连斩不需要新的技能基类：三个 SkillData 用 combo 串联，分别配置倍率，再给自己加休息 Buff。

## 一个全局回合

```text
nextTurn：生成普通行动队列，发 turn/sort
→ processBeforeTurn：回盾、回合前 Buff、规则登记追加行动
→ waitInput：按循环类型收指令或准备自动行动
→ 按行动记录逐条执行，完整动作后自动处理破盾大招并等待动画
→ processAfterTurn：回合后 Buff、过期处理
→ finishTurn：回合上限检查
```

PC 是轮到当前单位才推进输入边界并等待该单位输入；西游与烟雨在统一输入阶段推进各单位输入边界。插入行动不重复调用 `inputStart`。

## 完整 action 与动作后任务

`fight.resolveAction(run)` 接管一次动作的开始和退出。连招、反击、反伤、协战等嵌套结算完成后，才执行 `afterAction` 中的自动复活/受伤计次反应，再检查胜负，战斗未结束时由实际破盾者自动施放装配的大招（每队每回合一次，无大招则跳过）。

每个 `FightSide.ultimate` 只保存本队的一个usedTurn和一个pending。Fight只记录双方中最先登记者，在完整动作收尾先取走双方pending，再按登记顺序施放；先取走可避免第一招的嵌套动作收尾提前执行另一边。失败动作丢弃双方pending，已有胜负阻止后续大招，阵营绑定到新战斗及Loop初始化时重置。验证见 [阵营大招](../../tests/core/skill/test_side_ultimate.ts)。

单体攻击和群体结算分别通过 `magicAttackFunc`、`multiFunc` 建立动作作用域，内部函数处理具体效果。复用结算走这两个入口，以共享反应预算并保留动作结束回调。普通攻击、反击和协战共用 `AttackChecks.ts` 中的存活、禁攻击和原地技能检查，各流程分别负责目标资格、反击封印和协战次数。

动作外调用 `afterAction` 会直接执行；宿主组合多个底层操作时，需要主动包在同一个 `resolveAction` 内。异常作用域丢弃未处理任务，失败动作的 `FightContex` 视为废弃。群体目标和协战标记仅在正常返回时恢复。底层抛错，驱动捕获后仅在结果为 -1 时判攻击方失败，已有结果保留，详见 [排错](./排错与维护.md)。

## 属性基础与运行状态

- `attrOri`：单位重算属性的基础。临时 Buff/Rule 不应直接修改它。
- `attr`：当前资源及已合并被动、Buff、Rule 的属性。
- `attrDirty`：属性缓存是否失效，默认 true；Buff、被动、AI、Rule 修改后置脏，读取 `attr` 时计算并清除，构造末尾仍统一计算一次。`calcAttr()` 可显式立即重算；修改 `attrOri` 后需置脏或调用此入口。不要跨属性来源变化长期保存旧 `attr` 引用。
- Loop 在完整行动结束和下一行动出队前刷新所有脏单位，再统一重排剩余行动；烟雨即时技能同样刷新。顺序变化才同步行动条，不再监听 `speed` 事件驱动排序。`attr/speed` 事件仍在实际重算时发送；宿主动作外需要立即重排，可调用 `loop.onChangeSpeed(unit)`。
- 重算从基础与原配置重新合并，不能累计成长。
- Buff 死亡清理后重算，复活不会带回已经移除的属性加成。
- 随机一律经过 `Fight.random()`，当前为 Mulberry32 v1；改变抽样顺序会改变同种子的后续结果。
