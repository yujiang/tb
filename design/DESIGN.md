# tb 战斗库详细设计

状态：P0 已实现，P1/P2 仍为设计。已实现接口与使用方式见 [API.md](./API.md)，运行入口见 [README.MD](./README.MD)。本文中的未来接口草图不代表全部已经可用。

依据：README.MD。周边服务和库使用 TypeScript，因此本文采用 TypeScript 描述接口；代码示例用于解释契约，不是已经存在的 API。第一版优先完成 README 中的「库」和「最简单示例」，其他能力分阶段落地。

## 1. 目标与边界

tb 是独立于显示、网络和存储的回合制战斗引擎。

输入是初始战场、规则、种子和外部指令；输出是战斗状态、待输入请求、战斗事件和最终结果。相同的输入及规则版本必须得到相同的结果。

使用者可以在服务端运行权威战斗，也可以在客户端运行单机战斗。引擎不自行启动定时器，不访问网络、数据库、文件或系统时间。战斗动画播放多久、玩家等待多久，都由宿主处理。

主要设计目标：

1. 能单独运行、单步推进、复现问题和批量测试。
2. 数值与玩法可扩展，不强制所有游戏都有血、蓝、防御、速度。
3. 内置有限的常用机制，通过组合形成规则，而不是为每个游戏复制整个引擎。
4. 执行顺序明确，尤其是 Buff、反击、死亡、复活和胜负判定。
5. 为命令行编辑器、数据表和录像保留稳定的数据边界。

第一版不做通用脚本语言、可视化编辑器、网络同步框架、复杂寻路或任意时间点回滚。也不承诺不同代码版本之间直接重算同一份旧录像。

## 2. 总体结构

```text
宿主：单机 / 游戏服务器 / CLI / 批量模拟器
       │ commands、signals             ↑ events、requests、views
       ▼                              │
Battle：状态机、输入校验、推进、执行边界
       ├── TurnPolicy：行动机会、输入批次、轮次
       ├── Rules：数值、目标、技能、效果、死亡、胜负
       ├── EffectRunner：效果队列、触发器、结算窗口
       ├── World：单位、技能实例、Buff、空间、扩展状态
       └── Runtime：随机数、ID、序号、记录、快照
```

对外主要入口只有 `Battle`。其他模块通过明确接口协作；不要暴露可直接任意修改的内部 World。

采用显式实体和组件式数据，不引入完整 ECS 框架。战斗规模通常较小，先保证执行逻辑容易理解和调试。

## 3. 数据：定义、实例、规则分开

### 3.1 三类数据

| 类别 | 示例 | 生命周期 |
| --- | --- | --- |
| 定义 Definition | 单位模板、技能定义、Buff 定义 | 一场战斗中只读，可共享 |
| 实例 Instance | 当前资源、冷却、Buff 层数、站位 | 随战斗变化，必须可序列化 |
| 规则 Rules | 伤害公式、选目标、行动调度 | 注册的代码，使用稳定 ID 与版本识别 |

定义只包含 JSON 数据和处理器 ID，不嵌入函数。实例不保存函数、闭包、循环引用或宿主对象。恢复时用相同规则注册表重新绑定处理器。

### 3.2 Object 的处理

README 将单位、技能、Buff 统称为 Object。实现上可以共享 ID、定义引用和标签，但不把它们做成一个拥有所有能力的巨型基类。

```ts
type EntityId = string;
type DefinitionId = string;
type TeamId = string;
type JsonValue = null | boolean | number | string
  | JsonValue[] | { [key: string]: JsonValue };

interface EntityBase {
  id: EntityId;
  definitionId: DefinitionId;
  tags: readonly string[];
}

interface UnitState extends EntityBase {
  teamId: TeamId;
  controllerId: string;
  life: 'active' | 'dead' | 'removed';
  position: JsonValue;
  attributes: Record<string, number>;
  resources: Record<string, number>;
  skillIds: EntityId[];
  buffIds: EntityId[];
  custom: Record<string, JsonValue>;
}

interface SkillState extends EntityBase {
  ownerId: EntityId;
  cooldown: number;
  uses: number | null;
  custom: Record<string, JsonValue>;
}

interface BuffState extends EntityBase {
  ownerId: EntityId;
  sourceId: EntityId | null;
  stacks: number;
  duration: JsonValue;
  custom: Record<string, JsonValue>;
}
```

这些是建议形状。实现时对外提供只读投影；动态字典的合法键、范围和默认值由规则包校验。各游戏可以在规则层提供带类型的访问函数。

`teamId` 表示阵营，`controllerId` 表示指令归属：同一玩家可控制多个单位，同一阵营也可有多个玩家。AI 接管不需要改变阵营。

死亡单位保留在 World 中供复活、录像和来源追溯使用。移除单位同样保留必要的墓碑记录，但不再参与选目标和行动。

### 3.3 数值不写死在内核

内核不直接读取 `hp` 判断死亡，也不默认存在 `attack`、`defense` 或 `mp`。

基础规则包提供常见工具：

- 属性：基础值与修正项，例如攻击、防御、最大生命。
- 资源：当前值，例如生命、蓝、护盾或怒气。
- 数值修正：加法、比例、覆盖、上下限。
- 资源扣除、恢复、死亡检测的通用执行流程。

具体公式由游戏规则负责。示例规则使用：

```text
damage = max(1, attack - defense)
actualDamage = min(target.hp, damage)
target.hp = target.hp - actualDamage
hp == 0 → 请求死亡结算
```

属性与资源分开：最大生命是属性，当前生命是资源。最大生命改变时是截断、按比例变化还是保留当前值，由规则明确选择。

属性修正推荐固定流水线：`基础值 → 固定加法 → 比例加法 → 独立乘法 → 覆盖 → 上下限`。同一阶段用稳定排序；每个阶段的取整方式由数值规则固定。第一版示例只用整数加减，不先实现整套属性框架。

## 4. Battle 的状态与公共接口

### 4.1 对外状态

| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| created | 已构建，尚未开始 | 检查初始状态、start |
| running | 存在可继续执行的逻辑 | advance |
| waitingInput | 等待一个或多个输入 | submit |
| suspended | 在安全边界暂停，等待剧情等信号 | signal |
| finished | 已有胜负或规则指定的结束结果 | 查询、导出 |
| faulted | 引擎或扩展执行失败 | 查询错误、导出诊断 |

`waitingInput` 是引擎主动让出控制权，不是异步函数等待。不得在一次技能结算到一半时进入等待输入。战斗内反应若需要玩家选择，必须作为显式安全边界单独设计，第一版不支持交互式反应。

### 4.2 建议 API

```ts
interface Battle {
  start(): OperationResult;
  getView(): BattleView;
  getPendingInputs(): readonly InputRequest[];
  submit(command: BattleCommand): SubmitResult;
  signal(signal: BattleSignal): OperationResult;
  advance(options?: { maxSteps?: number }): AdvanceResult;
  snapshot(): BattleSnapshot;
}

interface AdvanceResult {
  reason: 'waitingInput' | 'suspended' | 'finished' | 'budget' | 'faulted';
  events: readonly BattleEvent[];
  steps: number;
}
```

`start()` 处理开场初始化及开场效果，到达安全边界后返回。`submit()` 只校验并记录输入，不直接执行战斗；宿主随后调用 `advance()`。这让日志归属、网络响应和单步调试更清楚。

`maxSteps` 限制本次调用处理的顶层调度步骤；一次技能及其反应链不可被这个预算切成两半。预算耗尽不代表平局，也不影响下一次推进的结果。

外部指令错误返回结构化错误，不改变状态，不消耗随机数。扩展处理器抛异常、出现非法数值或反应链超限则进入 `faulted`，不伪装为正常胜负。

第一版不实现通用回滚事务。`faulted` 战斗不能继续运行；失败时的内部状态仅供诊断，不能作为正常续战快照。宿主只转发完整成功提交的事件批次。

## 5. 将「轮」「行动机会」「行动」分开

这三个概念不能混用：

- Round：轮次，提供回合前后等全局时机。
- Opportunity：某单位获得的一次行动机会。
- Action：该机会最终执行的动作，例如技能、待机。

反击和追击是动作，但默认不新增行动机会、不计入轮次进度。眩晕跳过一次机会，仍可算该单位已获得本轮机会。

### 5.1 TurnPolicy 的职责

`TurnPolicy` 管理当前轮、行动机会、顺序和等待哪些输入，状态必须可序列化。它不能直接修改生命或施加 Buff。

策略输出的调度步骤包括：

```text
RoundStart
RequestInput(batch)
ExecuteOpportunity(opportunity, intent)
RoundEnd
NoProgress
```

Battle 在每一步之后执行对应规则和安全边界处理，再把执行反馈交回策略。策略通过反馈得知单位死亡、加入、跳过或动作完成。

调度策略还要接收单位加入、死亡、复活、移除的通知。第一版采用一个按轮策略，不急于冻结过度通用的策略接口；第二种调度方式接入后再验证接口是否足够。

### 5.2 第一种：全部下完指令再行动

流程：

1. 开始新轮，执行 `RoundStart` 及其触发效果。
2. 冻结本轮行动名单；默认包含此时可参与战斗的单位。
3. 对可行动单位创建输入请求，等待全部请求完成。
4. 按稳定顺序生成本轮行动队列。
5. 逐个执行行动机会及其反应链。
6. 执行 `RoundEnd`，再次检查结束条件，然后进入下一轮。

顺序在收齐指令时冻结。第一版按配置的单位顺序执行；后续可用速度降序、技能优先级等规则。并列时用单位创建序号打破平局，不默认随机。

单位执行前若死亡或被移除，取消该机会。眩晕等状态在执行前重新判断，允许出现「收指令时正常，出手时被控制」。默认不退还已经支付的费用；尚未开始的动作尚未付费。

本轮中途加入或复活的单位默认下轮进入名单。规则需要立即行动时应显式添加额外机会，不能偷偷修改遍历中的队列。

### 5.3 第二种：轮到谁，谁下指令后行动

仍按轮冻结名单和顺序，但每次只请求当前单位的指令，收到后立即执行，再请求下一个。它与批量输入的区别是输入开放时间，而不必重写技能结算。

若希望「玩家任选一个未行动单位，下指令后立即行动」，则由策略开放一组请求，每次接受一个并结算后重新生成请求。这是单独的策略选项，不能用网络指令到达顺序意外决定整轮顺序。

### 5.4 第三种：速度条，可一轮行动多次

后续策略使用整数逻辑时间推进速度条，按阈值生成行动机会。没有实时计时器。

README 中「全部动过一次算一回合」在此具体定义为：轮开始后冻结存活参与者集合；集合中每个单位都获得过至少一次机会，或已死亡/移除，即完成本轮。快速单位在此期间可以获得多次机会。

为了避免绕过回合后时机：当最后一个参与者的机会结算完，先结束本轮，再生成后续机会，即使同一逻辑时刻还有其他单位就绪。

被眩晕而跳过的机会也计入覆盖集合。永久不能获得机会的单位不能无限阻塞本轮：策略必须明确将其排除，或生成可计数的跳过机会。若没有任何单位能够推进，返回 `NoProgress`，交由停滞规则终止或等待外部输入，禁止空转。

速度变化、零速度、复活、同刻就绪的排序均属于该策略的契约。速度条策略在后续阶段实现，第一版只保留 `opportunityId` 和可保存的策略状态。

## 6. 指令：提交校验与执行校验

```ts
interface InputRequest {
  requestId: string;
  batchId: string;
  opportunityId: string;
  actorId: EntityId;
  controllerId: string;
  // 可选动作的结构化描述，不是执行器闭包。
  options: readonly JsonValue[];
}

interface BattleCommand {
  commandId: string;
  requestId: string;
  actorId: EntityId;
  actionId: string;
  targetIds: EntityId[];
  params: Record<string, JsonValue>;
}
```

一次请求默认只接受一条指令。第一版不支持修改已提交指令。批量模式中，每个请求有独立生命周期；其他单位先提交不使当前请求失效，不用全局状态版本粗暴拒绝并行输入。

提交时检查：请求存在且开放、单位匹配、动作可用、参数合法、目标数量及当前可选性正确。身份认证在网络适配层完成，适配层必须确认发送者拥有请求对应的 `controllerId`；核心中的 ID 不能代替认证。

执行时再次检查：行动者是否存活、是否被控制、技能冷却和资源是否足够、目标是否仍合法。提交成功表示引擎接受意图，不保证最终施放成功。

对失效意图定义策略：

| 情况 | 默认处理 |
| --- | --- |
| 行动者死亡或移除 | 取消机会，发出原因事件 |
| 无法行动 | 跳过机会，发出原因事件 |
| 唯一目标死亡或不可选 | 整个动作失败，不付费 |
| 多目标部分失效 | 依技能目标规则保留合法子集，或整体失败 |
| 资源不足、技能不可用 | 转为待机，记录失败原因 |

自动重选目标只能由技能或规则显式开启，不默认替玩家改指令。重新请求指令可能暴露本轮已经发生的信息，也会引入新的等待边界，第一版不采用。

`commandId` 用于幂等：相同 ID、相同内容重试返回原结果；相同 ID、不同内容拒绝。保存已接受指令及其结果，使恢复后重试仍然幂等。传输层畸形包和身份错误由宿主记录，不进入可重算的战斗输入流。

## 7. 一次动作如何结算

推荐固定管线：

```text
机会开始
 → 检查行动资格
 → ActionBefore 触发及结算
 → 再校验施法资格、费用和目标
 → 扣除费用，写入冷却
 → 解析技能效果
 → 顺序执行效果及其反应链
 → ActionAfter 触发及结算
 → 机会结束
 → 检查剧情、波次、胜负
```

`ActionBefore` 可能使行动者死亡或改变资源，因此付费前必须再检查。动作正式开始后费用不因未命中、伤害为零或目标随后死亡而自动返还。退款作为显式效果。

技能描述「产生哪些效果」，效果执行器负责「如何改变状态」。技能不能直接写目标生命来绕过护盾、减伤、受伤触发和死亡流程。

### 7.1 效果

```ts
interface EffectSpec {
  type: string;
  sourceId: EntityId | null;
  targetIds: EntityId[];
  params: Record<string, JsonValue>;
  tags: string[];
}
```

常见效果：伤害、治疗、资源变化、添加/移除 Buff、移动、召唤、复活、增加行动机会。效果执行器按 `type` 注册，内核不需要了解所有玩法。

效果队列采用显式栈帧调度，不依赖 JavaScript 递归。规则发出的反应效果在当前效果收尾后插入队首，先完整结算该反应链，再执行技能的下一个效果；同层按固定顺序插入，不能因逐项 `unshift` 意外反转。

例如「攻击 → 受伤反击 → 反击附带治疗」应完成整条反应后，再执行技能的第二段攻击。

每条效果记录 `effectId`、`parentEffectId`、`actionId` 和深度。反击不默认再次触发反击，通过效果标签和触发条件阻断。还要设置每动作总效果数、总触发次数、最大深度等硬上限，超限进入 `faulted` 并输出因果链。

### 7.2 修改窗口与事实事件分开

不能用一个任意事件总线承担所有业务。

- 修改窗口：结算前开放的受控上下文，例如伤害倍率、吸收量、取消标记。规则只能修改允许的字段。
- 事实事件：已经发生的结果，只读，例如最终扣血、Buff 被移除、单位死亡。表现层和记录器订阅这些事件。

伤害流程：

```text
校验当前目标
 → 计算命中
 → 未命中则发出 Miss，结束本次伤害
 → 命中后计算基础伤害
 → DamageBefore：增减伤、免疫、护盾等修改
 → 统一取整与边界校验
 → 提交资源变化，记录 DamageApplied
 → DamageAfter：生成受伤、吸血、反击等后续效果
 → 死亡检查及死亡触发
 → 执行后续反应效果
```

`DamageApplied` 区分请求伤害、减免、护盾吸收、实际生命损失和过量伤害，避免表现与吸血公式误用数值。零伤害是否触发受伤由规则显式决定；第一版无暴击、命中或护盾，必定命中。

`DamageAfter` 可以提出后续效果，但不直接执行；致死目标先完成死亡检查，普通反击随后因来源已死亡而失效。亡语允许带 `allowDeadSource` 的专门效果。这样不依赖监听器执行顺序来决定「死人能否反击」。

### 7.3 多目标与同时结算

默认多目标按稳定目标顺序逐个结算，目标列表在效果开始时冻结。顺序结算会影响反击、死亡触发和后续目标，必须在技能定义中可以看出。

「同时对双方造成伤害」需要专门的结算组：先基于组开始状态计算全部数值，再统一提交资源变化，统一完成死亡检测，最后生成反应。结算组内不得夹入普通触发器。第一版不实现同时结算组，也不将顺序群攻描述成同时发生。

### 7.4 死亡与复活

数值规则检测是否满足死亡条件；核心执行统一的生命状态转换：

```text
发现死亡候选
 → BeforeDeath：允许保命规则阻止
 → 重查死亡条件
 → 标记 dead，取消后续普通机会
 → 发出 UnitDied
 → 收集死亡触发与 Buff 清理
 → 调度后续效果
```

同一次死亡转换只发出一次 `UnitDied`。死亡触发按死亡发生时的规则快照收集，然后清除约定在死亡时移除的 Buff；被清除的 Buff 仍可执行已经收集的死亡触发。

复活使用显式效果，恢复生命状态和规定资源，发出 `UnitRevived`，通知调度器；不得仅把死亡单位的生命加到正数就隐式复活。

## 8. Buff 与时机

### 8.1 统一触发器

被动技能、Buff、场地效果和关卡规则可以使用同一个触发器结构：

```text
窗口/时机 + 条件处理器 + 优先级 + 次数限制 + 效果处理器
```

常见时机包括：战斗开始、回合前后、机会前后、动作前后、命中、伤害前后、治疗前后、死亡前后、Buff 增删、波次切换和战斗结束。

这些是有类型的流程节点，不是任意字符串广播。每个节点明确哪些字段可改、能否取消、是否允许产生效果。

### 8.2 稳定触发顺序

同一窗口中的触发器排序键：

```text
priority 降序 → owner 创建序号升序 → 实例创建序号升序 → 定义内触发器序号升序
```

调度时冻结触发器列表；轮到执行时重新判断其来源是否仍有效。窗口中新添加的 Buff 不加入本次列表，移除的 Buff 不再响应后续节点。已生成的独立效果是否因来源失效而取消，由效果类型约定。

优先级只控制同一窗口，不允许用优先级跨越「伤害前」「伤害后」等阶段。

### 8.3 叠加与持续时间

Buff 定义必须声明：

- 叠加键：按定义合并，还是按定义和施加者合并。
- 重复施加：忽略、刷新、加层、独立实例或替换。
- 最大层数，以及到达上限后是否刷新。
- 持续时间的时钟：全局轮次、持有者机会、持有者动作次数或永久。
- 死亡、驱散、来源移除时的保留规则。

持续时间计数不能只有含糊的 `duration: 1`。例如「持续 1 个后续 RoundEnd」在第 3 轮中添加，应在第 3 轮末触发后过期；若玩法需要到第 4 轮结束，必须选不同计数语义。

建议计时描述为 `{clock, remaining, expirePhase, skipCurrentBoundary}`。到达计时边界时先执行应有触发，再扣计数并过期，或明确指定先过期；同一规则包必须保持一致。新 Buff 是否计入当前边界，用边界序号和 `skipCurrentBoundary` 判断，避免依赖遍历位置。

第一版先不实现 Buff 系统，但效果、生命周期事件和创建序号应保留扩展位置。第二阶段用中毒和眩晕验证设计：中毒验证周期触发及死亡，眩晕验证机会跳过及持续时间。

## 9. 空间与选目标

空间只描述逻辑位置，不包含像素、动画坐标或场景对象。

通过 `SpacePolicy` 封装：

```text
validatePosition / canOccupy / query / distance / move
```

初始提供 `SlotSpace`：阵营内固定站位，使用 `{ side, slot }`。以后可增加行列格子、前后排、阵法或没有位置限制的集合空间。

选目标拆为两步：

1. 查询候选：敌我关系、生命状态、标签、空间范围。
2. 规则选择：指定目标、随机、最低生命、全体、前排优先等。

候选集合必须先稳定排序，再执行随机或取前 N 个。技能声明是施放时锁定目标列表，还是每段效果重新选择目标。

阵法可同时提供站位限制和属性修正，不需要修改 Battle 主循环。阵营关系由关系规则判断，保留召唤、中立、混乱和多阵营扩展空间；第一版只支持两个敌对阵营。

## 10. AI 只是指令生产者

AI 读取与其权限相符的战斗视图及输入请求，生成普通指令，经过与玩家相同的校验。它不直接调用伤害函数，不绕过资源或冷却。

基础 AI：合法目标随机、攻击最弱目标、优先治疗、固定优先级。Boss AI 在此基础上增加可序列化的阶段状态、条件和技能序列。

AI 状态保存在宿主或明确的控制器状态中，不能藏在闭包里。若恢复后需要继续自动战斗，必须一并恢复。

AI 使用独立随机源，避免 AI 多做一次候选抽样就改变后面的伤害随机。权威实例记录 AI 生成的指令；重算时直接输入指令，不要求再次执行 AI。

第一版 AI 固定选择第一个合法敌人，完全确定，无需 AI 随机。随机 AI 在后续加入。

## 11. 胜负、多波与暂停

### 11.1 结束条件

胜负规则返回结构化结果：胜方阵营列表、败方阵营列表、平局或脚本结束，以及原因。

检查时机：开场效果完成后、每个完整动作及反应链完成后、回合后效果完成后、波次/剧情安全边界完成后。不能在伤害刚把一人打到零时就立即宣布胜利，否则会截断亡语、复活或双方同归于尽。

默认规则：一方没有存活战斗单位则另一方胜；双方都没有则平局。复活待处理、增援和下一波是否阻止结束，由遭遇规则先处理。

战斗结束只提交一次结果，发出 `BattleFinished`，清空输入请求。结束后的展示和清理钩子不能再产生会改变胜负的战斗效果。

### 11.2 遭遇与多波

`EncounterPolicy` 管理波次、增援和剧情。安全边界上的优先顺序为：

```text
当前动作及反应链清空
 → 检查双方是否已无继续资格等终局条件
 → 检查是否触发剧情/下一波/增援
 → 执行转换效果，再检查边界
 → 判断当前遭遇是否结束
```

例如玩家已全灭，默认不再切下一波；敌人清空但还有下一波，则先转换，不把本波胜利当成整场胜利。转换规则需要声明是否允许逆转玩家全灭这样的默认终局条件。

连续转换也有次数上限，防止空波配置造成死循环。第一版只有一波，先实现简单结束规则。

### 11.3 暂停插入对话

剧情在安全边界发出 `Suspended` 事件，附带 `suspendId` 和数据，然后暂停推进。宿主播放对话，再发送匹配的 `Resume` 或选择信号。

信号属于会影响结果的外部输入，必须校验、幂等并记录。等待本身不推进回合、Buff 或冷却。恢复后先完成待处理的遭遇转换，再开放新指令。

## 12. 确定性约束

确定性不是只设置一个随机种子，还要约束执行方式。

1. 战斗内随机只能通过引擎随机源；禁止 `Math.random()`。
2. ID 由单调计数器生成，不使用时间或随机 UUID。
3. 所有影响结果的集合遍历、排序和平局处理都显式规定顺序。
4. 规则不读取系统时间、网络或进程全局可变状态。
5. 资源、计数和随机算法使用明确整数范围，拒绝 NaN、Infinity 和不安全整数。
6. 比例推荐使用万分比整数；乘除顺序、取整和溢出处理必须固定。超出安全整数范围时使用明确的大整数规则或拒绝，而不是默默失真。
7. 记录引擎版本、规则包版本、内容摘要、初始状态和种子。
8. 快照保存随机源内部状态、计数器、策略状态、输入请求、已接受输入及扩展状态。

随机源实现应固定具体算法及版本，并用参考向量测试。接口至少包括 `nextUint32()`、无偏的 `int(min, maxExclusive)`、导出与恢复状态。第一版可以选一个实现简单的 32 位 PRNG，但应在实现时写明名称、零种子处理和版本，不把随机算法作为可悄悄替换的内部细节。

条件不满足时不能保证结果相同：自定义规则具有完整代码能力，确定性依赖规则遵守契约。提供重复执行与恢复比对测试帮助发现违规。

## 13. 事件、录像和快照

### 13.1 事件模型

```ts
interface BattleEvent {
  seq: number;
  type: string;
  round: number;
  opportunityId: string | null;
  actionId: string | null;
  effectId: string | null;
  parentEffectId: string | null;
  payload: JsonValue;
}
```

典型事件：轮开始、指令请求、动作开始、动作失败、伤害、治疗、资源变化、Buff 增删、死亡、复活、轮结束、波次变化、暂停、结束。

`seq` 全场单调递增，供增量拉取、去重和断线恢复使用。一个 `advance()` 的结果可以包含多个已提交安全边界的事件批次；效果链失败时不发布该失败边界的普通事件，单独返回故障信息。

事件描述逻辑事实，不包含「等待 500ms」「播放某个引擎动画」等显示指令。表现层使用动作及父子效果关系安排动画。

### 13.2 两种不同的录像

**可重算记录**：初始配置与数据版本、种子、已接受指令、剧情信号，以及可选状态摘要。用于复现、验证和回归测试。

**表现事件记录**：初始展示状态、表现所需的结果事件和事件协议版本。用于不重新运行逻辑的播放。要支持任意进度跳转，还需周期性展示快照。

这两类记录可以同时保存，但不能把零散调试日志当成完整录像。第一版实现可重算记录和 JSON 事件输出；完整表现播放器后续实现。

### 13.3 快照

只允许在没有执行中效果链的安全边界创建有效快照：等待输入、已完成的调度步骤之后、剧情暂停、结束时。快照不能包含函数和未序列化的执行栈。

快照包含 World、轮次与调度状态、待输入请求、已提交指令、随机源状态、序号与 ID 计数器、规则扩展状态、暂停状态及版本元数据。

恢复时验证版本与内容摘要，不匹配则拒绝或通过显式迁移器转换。不要静默用新数据恢复旧战斗。

状态摘要使用规范化序列化：对象键排序，数组保留语义顺序，拒绝不可序列化数值。第一版不要求密码学防篡改；防作弊签名属于宿主。

### 13.4 日志体积

内核不强制永久保留所有事件。通过事件批次交给宿主落盘或流式消费；幂等指令记录和输入录像也可由宿主按战斗生命周期归档。需要控制进程内保留量，避免长战斗占用无限内存。

## 14. 单机与网络接入

单机路径：

```text
输入/UI → submit → advance → 事件 → 展示
```

服务端路径：

```text
网络鉴权/控制权检查 → 指令解码与限流 → submit → advance
                                                 ↓
                                  事件投影 → 各客户端
```

超时由宿主决定。宿主可在超时后代交待机或 AI 指令；这些必须作为普通输入记录，不能由内核读取当前时间自动改变结果。

同一 Battle 实例串行处理输入和推进，禁止回调重入。并行发生在不同战斗之间，可由宿主分配 worker。

客户端默认消费权威结果，不要求锁步。若后续增加客户端预测，仍以相同逻辑运行，但预测回滚属于额外功能。

`getView()` 是供可信宿主使用的只读完整视图，不直接暴露给所有玩家。宿主按玩家权限投影隐藏技能、未公开指令、随机状态等信息；也可注册专门投影器。跨玩家信息隔离由投影与传输层验证。

## 15. 数据驱动

运行时读取经过校验的 JSON 定义，表格只是生产这些 JSON 的一种方式。核心不依赖 Excel、CSV 或某个编辑器。

推荐数据管线：

```text
表格/手写 JSON → 导入转换 → schema 校验 → 引用校验
             → 规则参数校验 → 内容摘要 → 不可变 DefinitionCatalog
```

技能示例：

```json
{
  "id": "normal_attack",
  "targetRule": "one_living_enemy",
  "costs": [],
  "cooldown": 0,
  "effects": [
    { "type": "damage", "formula": "attack_minus_defense" }
  ]
}
```

数据引用注册的公式和处理器 ID，不执行任意字符串代码，不用 `eval`。特别复杂的 Boss 技能通过代码注册处理器，仍由数据引用。

构建前检查重复 ID、丢失引用、非法数值、无效处理器、Buff 叠加配置和空间位置。战斗开始后冻结定义；热更新只影响新建战斗，已有战斗继续使用原版本。

第一版手写定义对象并做必要校验，不先做表格导入工具和通用 schema 生成器。

## 16. 最小示例的具体行为

示例固定以下规则，避免「可配置」导致示例没有确定含义：

| 项目 | 第一版约定 |
| --- | --- |
| 阵营 | A、B 两个敌对阵营 |
| 数值 | 攻击、防御、当前/最大生命，均为安全整数 |
| 空间 | 每方固定槽位 |
| 调度 | 每轮收齐全部指令，按初始单位顺序行动 |
| 每轮次数 | 每个轮开始名单内的单位一次机会 |
| 动作 | 普通攻击、待机 |
| 命中 | 必定命中，无暴击 |
| 伤害 | `max(1, 攻击 - 防御)`，实际扣血不超过当前生命 |
| 失效目标 | 动作失败，不自动重选 |
| AI | 选择第一个合法敌人；没有则待机 |
| 死亡 | 生命为零标记死亡，取消后续机会 |
| 胜负 | 一方全灭则另一方胜，双方全灭则平局 |
| 防停滞 | 配置最大轮数，到完整回合结束仍未分胜负则按规则判平 |

演示战斗：

```text
A：HP 10，攻击 5，防御 1
B：HP  8，攻击 4，防御 2
顺序 A → B

第 1 轮：A 打 B 3 点，B 剩 5；B 打 A 3 点，A 剩 7。
第 2 轮：A 打 B 3 点，B 剩 2；B 打 A 3 点，A 剩 4。
第 3 轮：A 打 B，请求 3 点，实际扣 2 点；B 死亡。
当前动作结算结束，A 获胜；B 不再执行已提交指令。
```

示例应可无网络、无界面运行，输出简短文字战报和 JSON 事件，并能用记录重算得到相同结果。最大轮数和空阵营开局都必须有确定行为。

示例驱动代码的预期形状：

```ts
const battle = createBattle({
  rules: createSimpleRules(),
  definitions: simpleDefinitions,
  setup: exampleSetup,
  seed: 12345,
});

const started = battle.start();
consumeEvents(started.events);
while (true) {
  const result = battle.advance({ maxSteps: 100 });
  consumeEvents(result.events);
  if (result.reason === 'waitingInput') {
    for (const request of battle.getPendingInputs()) {
      battle.submit(simpleAI.choose(battle.getView(), request));
    }
  } else if (result.reason === 'finished' || result.reason === 'faulted') {
    break;
  } else if (result.reason === 'suspended') {
    break; // 真实宿主等待剧情信号。
  }
}
```

上面循环仅用于说明推进方式；实际宿主还需检查启动和提交结果，对故障和非法指令作明确处理。

## 18. 分阶段实现

### P0：打通库与最简单示例

- 确定性 ID、随机源、World 及只读视图。
- Battle 生命周期、结构化错误、指令请求与幂等提交。
- 按轮批量收指令和固定顺序调度。
- 普通攻击/待机、伤害提交、死亡和结束规则。
- 槽位空间和基础选目标。
- 事件输出、可重算输入记录、安全边界快照恢复。
- 固定 AI 的攻防血示例。

P0 不实现 Buff、速度条、多波、剧情暂停、表格导入或完整 CLI。状态枚举和数据格式可留扩展位，但不要求每个未来功能都有空实现。

验收：示例正常结束；记录可复现；等待输入时恢复后结果一致；错误输入不改变状态；不同推进预算不改变最终结果。

### P1：用真实玩法验证扩展点

- 逐个单位收指令的策略，验证调度与结算的分离。
- 治疗、费用、冷却和属性修正。
- Buff、触发窗口、中毒、眩晕、简单反击。
- 明确冷却采用全局轮次还是持有者机会计时，复用计时边界模型。
- 多波、暂停信号、复活及相关边界测试。

只有第二种实际实现需要时再调整扩展接口，避免先设计一个无所不包的框架。

### P2：常用机制与生产工具

- 速度条策略、额外行动和同时结算组。
- 随机/治疗/阶段式 AI。
- 数据导入与校验、命令行编辑器、录像播放及检索。
- 跨版本迁移、性能分析与批量模拟。

## 19. 验证重点

测试重点是规则边界及可复现性，不按每个类机械编写一组测试。

| 场景 | 必须验证的性质 |
| --- | --- |
| 最小示例 | 第 3 轮 A 胜，实际扣血和事件顺序正确 |
| 重复执行 | 相同输入、种子、版本的状态和事件一致 |
| 分段推进 | 一次推进很多步与反复推进一步结果一致 |
| 快照恢复 | 保存/恢复后的后续事件与不中断运行一致 |
| 并行输入 | 无顺序依赖的同批指令交换到达顺序，最终战斗结果相同 |
| 指令重试 | 不重复行动、不重复付费，冲突 ID 被拒绝 |
| 非法指令 | World、随机状态和请求生命周期均不变化 |
| 行动前死亡 | 已提交的普通动作不会继续执行 |
| 空战场、轮数上限 | 明确结束，不空转 |
| 同速/同优先级 | 稳定顺序，不依赖容器遍历偶然性 |
| Buff 边界 | 新增、移除、刷新和过期不重复触发 |
| 反击/亡语 | 因果链明确，胜负检查不截断反应 |
| 异常扩展/无限触发 | 可诊断地 faulted，不卡死、不伪造正常结果 |
| 多波与暂停 | 不提前结束，恢复信号幂等 |
| 数值越界 | 拒绝非法数值，生命不溢出约定范围 |

同批输入的录像接收顺序可以不同，但解析后的动作顺序、战斗状态与战斗事实事件应相同；不要要求包含提交审计顺序的整个原始记录逐字节一致。

P0 只执行与其功能对应的验证，后续功能加入时补上相关测试。性能先测真实规模，不以引入复杂缓存和对象池为前提。

## 20. 关键取舍

1. **采用模块组合，避免深继承。** 单位、技能、Buff 有不同职责；共享数据约定比统一大基类更容易保存和扩展。
2. **调度先与结算分离。** 不同回合机制改变何时获得机会，技能效果依然走同一管线。
3. **规则负责游戏语义，内核负责执行秩序。** 内核不包揽所有数值，却要固定输入、效果、触发、死亡和结束的边界。
4. **确定性与记录从第一版就有。** 后补会迫使规则、ID 和状态保存整体重做。
5. **先用最小示例证明可运行。** Buff 等复杂机制通过下一批具体场景检验，不一次性完成所有抽象。

实施默认：TypeScript、可信代码规则扩展、权威实例串行执行、整数数值、按轮批量输入、固定顺序行动。后续若具体游戏规则不同，应更换对应策略和规则包，保持输入与执行边界不变。
